# CLAUDE.md

Project standard for Claude Code. Written for Claude, dense on purpose.
This file is the same in every repo and is replaced as a whole on updates. Do not edit it per project.
Project facts live in docs/project.md, imported here. Keep this file under 200 lines.

@docs/project.md

## Context rules
- Read as little as possible. Lookup order: docs/project.md -> docs/architecture.md -> docs/modules/<name>.md -> git log -> code.
- Before reading a diff or file history: `git log --format=%B -n 15 -- <path>`. Commit bodies explain why.
- Search with rg/fd, read only the matching ranges, not whole files.
- Delegate broad search, log reading and exploration to the scout agent. Keep only its conclusion.
- Never read: lockfiles, build output, generated code, CHANGELOG.md, vendored deps.
- Task touches more than 3 files: write a plan to tasks/<id>.md first, then implement from the plan.
- Context getting long: write state to handoffs/<id>.md and ask the user for a fresh session.
- No recap of unchanged code in answers. Report: what changed, where, what is open.

## Knowledge layout
Source of truth is markdown in the repo. It is versioned and merges with the code.

| Path | Content | Rule |
|---|---|---|
| docs/project.md | name, stack, layout, language rules of this repo | max 40 lines |
| docs/architecture.md | modules, boundaries, data flow | max 200 lines |
| docs/modules/<name>.md | purpose, public interface, pitfalls | one per module |
| docs/decisions/NNN-title.md | decision, reason, rejected options | append only |
| tasks/<id>.md | goal, acceptance checks, owned paths | one per task |
| handoffs/<id>.md | result, changed interfaces, open points | written at task end |
| .claude/skills/<name>/SKILL.md | one repeatable multi-step procedure | only after user approval |
| <subdir>/CLAUDE.md | rules valid only in that subtree | optional |

- Doc style: terse key facts, lists, tables. No prose, no filler. Readability for humans is secondary.
- Code change that affects a doc: update the doc in the same commit.
- No vector DB by default. If added: MCP server, derived index only, rebuildable with `task index`,
  each entry stores commit hash + path. Commits never reference index IDs.

## Skills
- Skills live in .claude/skills/<name>/SKILL.md and are versioned with the repo.
  Frontmatter: `name`, `description`. The description says when to use the skill, because that
  line decides whether it gets loaded. Body under 40 lines.
- The same multi-step procedure comes up a third time: propose a skill (name, one-line description,
  the steps), wait for user approval, then create the file. Never create or change one unasked.
- Before proposing, check .claude/skills/ for a skill that already covers it: propose an update instead.
- A skill describes a procedure, not facts. Facts belong in docs/.
- Skills call tasks from the Taskfile. They never duplicate the underlying tool commands.

## Tooling
- Taskfile is the only command interface. Discover with `task --list`. Do not call underlying tools directly
  if a task exists. Missing command: add a task, do not paste one-off shell lines.
- Standard task names: setup, dev, test (fast: unit + e2e smoke), e2e (full suite), lint, fmt,
  check (lint + types + test), ci (check + e2e + build), build, changelog.
- Tasks print nothing on success and the full output on failure. No output means it passed.
  To see everything: `task --output interleaved <name>`.
- Prefer modern tools over legacy ones: rg over grep, fd over find, jq for JSON,
  lefthook for git hooks. Language toolsets: see Stack.
  New dependency or tool: pick the current maintained option and record it in docs/decisions/.
- Changelog: generated by git-cliff via `task changelog`. Never edit CHANGELOG.md by hand.
- Permissions live in .claude/settings.json. A denied or prompted command is intended. Do not work around it.

## Stack
Defaults for new projects. Do not choose ad hoc.

| Case | Language | Toolset | E2E |
|---|---|---|---|
| default: CLI, services, tools | Go | cobra, golangci-lint v2 (lint + fmt) | testscript (txtar scripts) |
| low level or performance critical | Rust | clap, clippy, rustfmt, cargo-nextest | assert_cmd |
| mock, prototype, throwaway | Python or TypeScript | uv + ruff + pyright, or bun + biome + tsc | pytest or bun test, CLI as subprocess |
| Android app | Dart + Flutter | flutter analyze, dart format | integration_test, Patrol for native dialogs |

- Existing repo: its stack wins over these defaults.
- Deviation from the table: propose it with a reason, wait for user approval, record in docs/decisions/.
- No second language inside a repo without approval.
- Dependencies: prefer the standard library. Add one only if it removes real work.
- Source files stay under about 400 lines. Split by responsibility, so reads stay cheap.

## CLI contract
- Every command supports `--json`: the result as one JSON document on stdout, nothing else.
- Errors: non-zero exit, message on stderr. With `--json`: `{"error": "<message>"}` on stderr.
- stdout carries results only. Logs and progress go to stderr.
- E2E tests assert on the `--json` form where possible, not on human text.

## Environment (NixOS + flakes)
All development happens on NixOS. Every repo has a flake with a dev shell.

- flake.nix provides devShells.default with ALL tools: compiler, task, git-cliff, lefthook, linters, test deps.
  flake.lock is committed.
- .envrc contains `use flake` (nix-direnv). Sessions start inside the dev shell.
  If `task` is not on PATH, prefix every command with `nix develop -c`, also `git commit` (the hooks need the tools).
- Tool missing: add it to the dev shell. Never install imperatively or globally: no nix-env,
  nix profile install, go install, cargo install, pip install, npm -g, curl | sh.
- Flakes only see git-tracked files. `git add` new files before running nix commands.
- NixOS constraints: no FHS paths (/bin/bash, /usr/bin/python, /lib). Only /bin/sh and /usr/bin/env exist.
  Shebang is `#!/usr/bin/env bash`. Downloaded prebuilt binaries do not run. Take everything from nixpkgs.
- Go and Rust flakes expose packages.default, so `nix build` produces the program.
  Prototype stacks and Flutter need only the dev shell.

## Safety
- Never read, print or commit secrets: .env*, *.key, *.pem, secrets/.
- Never push to main, force push or rewrite published history.
- Destructive commands (deleting outside the repo, dropping data) need explicit user approval.

## Testing
Every program gets an e2e harness from the first commit. E2E is the primary safety net, unit tests are secondary.

- E2E tests drive the real entry point (CLI, HTTP API, UI) and assert on observable behavior, not internals.
- Services: the test starts the real binary on a free port and talks to it over the network.
- New project: first deliverable is a walking skeleton plus one passing e2e test, before any feature.
- New feature: write the e2e test from the acceptance checks first, in the full tier, and see it fail in
  `task e2e`. Then implement. Fast, central tests move to the smoke tier once they pass.
- Bug fix: reproduce with a failing test first. The test stays as a regression guard.
- Never delete, skip, loosen or mock away a failing test to get green. If a test is wrong, say so and ask.
- Deterministic only: seeded data, no real network or clock, isolated temp state per test. Flaky test = bug, fix it now.
- Smoke subset (under 60 s) runs in `task test` on every commit. Full suite runs in `task e2e`.
- Unit tests only where they are cheaper than e2e: pure logic, parsers, edge cases.
- Pipeline: CI runs exactly `nix develop -c task ci`, nothing else. No logic in CI config,
  so local and CI results match.

## Commits
Conventional Commits, parsed by git-cliff. One topic per commit.

```
<type>(<scope>): <summary, imperative, max 72 chars>

Why: <reason or problem>
What: <approach + key paths>
Impact: <API, behavior, migration; "none" if none>
Open: <known gaps; omit if none>

Refs: docs/decisions/NNN-title.md
Agent: <agent> (<model>)
```

- Types: feat, fix, refactor, perf, docs, test, build, ci, chore. Breaking change: `!` after scope
  plus `BREAKING CHANGE:` footer.
- The message must let a future session understand the change without opening the diff.
- Refs point to stable repo paths only, omit if none. Agent trailer only when an agent wrote the commit.
- Enforced by lefthook: commit-msg checks the format, pre-commit runs `task check`. Never use --no-verify or -n.

## Multi-agent work
Preferred for tasks that split into independent parts. Not for sequential or same-file work.
The lead is the main session. It plans, delegates, reviews and merges. It does not implement.

Before starting, the lead (or the architect agent) writes tasks/<id>.md containing:
1. Split into subtasks, each with owned paths. No path has two owners.
2. Shared interfaces (types, API contracts, schemas), fixed before parallel work starts.
3. Agent per subtask.
4. Acceptance checks per subtask (commands that prove done).

Agents and their models are fixed in .claude/agents/<name>.md, not chosen ad hoc:

| Agent | Model | Use |
|---|---|---|
| architect | opus | split, interfaces, acceptance checks. Writes tasks/<id>.md only |
| test-writer | sonnet | e2e tests from the acceptance checks, before implementation |
| worker | sonnet | implementation of one subtask |
| reviewer | opus | read-only review before merge |
| scout | haiku | search, summaries, simple checks. Read-only |

Isolation:
- test-writer and worker run in their own git worktree and branch (.claude/worktrees/). No forks.
- Worktrees start from the lead's HEAD and contain committed files only. Commit tasks/<id>.md before delegating.
- A worktree may have no dev shell loaded. If `task` is not on PATH, prefix commands with `nix develop -c`.
- An agent edits only its owned paths. Change needed elsewhere: request it in the handoff, do not edit.

Order per subtask: test-writer -> lead merges the test branch (`task check` passes, the new tests still fail
in `task e2e`) -> worker -> reviewer -> merge.
The agent that writes the e2e test for a subtask is never the one that implements it.

Communication:
- Default channel is files: tasks/<id>.md in, handoffs/<id>-<subtask>.md out, committed on the agent's branch.
- Interface change mid-task: stop and report to the lead. Never change a shared contract silently.
- Subagents report only to the lead. Use agent teams or cross-session messaging only when
  workers must negotiate during execution, and only if enabled in this install.

Merge:
- Only the lead or the user merges. An implementation branch is merged after `task ci` passed and the reviewer
  approved. Both run inside that agent's worktree, never in the lead's checkout (it has a different HEAD).
- After merge: delete branch and worktree, fold handoff facts into docs/, delete the task and handoff files
  (keep TEMPLATE.md).

## Done means
- Acceptance checks from the task file pass, `task check` passes, new behavior is covered by an e2e test.
- Affected docs updated, commit(s) follow the format above.
- Final message lists: changed paths, decisions made, open points. Nothing else.
